# Publishing Squabblemon patches

Patch notes and their in-game letters are a separate, deliberately narrow workflow from the unrestricted operator mail command. This workflow does **not** change card stats, send email/push notifications, or schedule a release. Merely deploying code, applying a migration, or saving a draft publishes nothing and grants nothing. **An authorized publish click on a live deployment is a real broadcast and needs its own approval.**

## Administrator access

Configure `PATCH_ADMIN_USER_IDS` **server-side** as a comma-separated list of exact Clerk user IDs for the intended environment. Do not put it in a `VITE_` variable or browser code. An unset or empty list denies every account; matching display names, emails, request headers, client flags, and the preview fixture do not grant access. Development and production Clerk accounts may have different IDs. Sign in as an allowlisted administrator and open `/game/admin/patches` directly. The server checks the authenticated Clerk session on **every** admin read and mutation; the page is only a convenience gate. Admin mutations additionally require a same-origin browser request. Use the existing Clerk/session configuration; no independent admin password is created.

## Before a live publish

1. Obtain separate approval for the intended **environment, version, text, audience, and per-player gift**. Do not use the disposable test runners on production, and do not use the operator `mail:ops all --apply` to simulate this workflow.
2. Confirm the exact deployment commit, its database branch, and the branch's applied native migration version `202610050001_patch-publication`. Inspect **that same branch** for `patch_drafts` and `patch_delivery_targets`, the version and patch/recipient unique indexes, foreign-key and status constraints, and gift/check constraints. A green build or a migration-file listing is not proof that the runtime branch has migrated. Use the provider's migration dry-run on the intended deployment if history is unclear; preserve already-applied migration bytes. Never run whole-schema push or manual production SQL to make a release appear ready.
3. Verify the scheduled `patch-delivery` function was included in the built deployment and has database access to the **same** branch as the API. The publishing request attempts a small initial batch; scheduled runs continue the remaining batches without an admin tab. Failure to deploy/run the worker leaves remaining deliveries pending, not magically complete.
4. On the private desk, create a draft with a unique version, calendar date, title, overview, and lists of buffs/other changes. Default gift is **50 Clout and 0 Pack Tickets**; choose 0 or 1 ticket, with no more than 100 Clout and 1 ticket per player. Save, then preview the exact Events copy, letter, gift, and the **current** audience count. Re-preview if anything changes. The audience preview is an estimate, not a reservation.
5. With explicit approval, type the displayed version in the publish confirmation. Publication atomically freezes the content, campaign identity, and the IDs of profiles present at that point. A concurrently edited draft fails the confirmation rather than publishing unreviewed copy. New profiles are not included. After publication the draft cannot be edited or published again.
6. Refresh the desk to monitor `delivered / intended`, pending and failed counts. The scheduled worker retries outstanding deliveries in bounded batches, stopping automatic retries after three failed attempts; the desk's retry control can request one batch for exhausted failures. Removed accounts stay in the audience ledger as undeliverable rather than disappearing from the intended count. Investigate persistent failures instead of creating another version or changing reward values. Events says delivery is underway while there is work to do, **partial** if some targets remain undeliverable, and complete only when every target was delivered. A player can read their letter in Mailman and claim the saved gift exactly once; receiving a letter never credits the wallet before a claim.

The `mail:ops` operator tool remains available for unrelated campaigns, with its own broader limits. Do not reuse a patch campaign ID for operator mail. A patch campaign ID and its content are stable across retries; the profile row lock, delivery ledger, and one-time claim transaction prevent duplicate letters and wallet credits.

## Local verification (never live data)

`env -u DATABASE_URL node scripts/test-events-feedback-database.mjs` provisions a disposable native PostgreSQL cluster and checks both standalone development SQL and Netlify-native SQL under the runner's transaction, plus backend route/delivery tests. It refuses a caller-supplied database URL. Run `pnpm run typecheck`, `node scripts/check-netlify-migrations.mjs`, and `node --test scripts/check-netlify-migrations.test.mjs` as release checks. From `artifacts/squabblemon`, run `pnpm exec playwright test patch-desk.spec.ts --config e2e/playwright.config.ts --project chromium-desktop --project chromium-phone` to exercise mounted Events, Mailman, and the desk with intercepted fixture API responses; these UI fixtures are not authorized accounts and cannot publish against the server. Browser tests do not replace the isolated database tests or a post-deploy branch/readiness check.

No live migration, announcement, deploy, or currency grant is part of local verification.
